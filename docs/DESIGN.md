# DESIGN.md

> แนวทางการออกแบบสำหรับเว็บแอปช่วยค้นหา จัดรายการ และแนะนำสินค้าที่จำเป็น  
> เอกสารนี้เป็นแหล่งอ้างอิงหลักสำหรับ Designer, Developer และ AI ที่สร้างหรือแก้ไขหน้าจอของระบบ

---

## 1. ภาพรวมผลิตภัณฑ์

ผลิตภัณฑ์นี้เป็น Mobile Web App สำหรับช่วยผู้ใช้ค้นหาสิ่งของที่จำเป็นในสถานการณ์ต่าง ๆ โดยเฉพาะเมื่อผู้ใช้ยังไม่รู้ว่าควรเริ่มต้นจากอะไร

ตัวอย่างสถานการณ์:

- เริ่มอยู่หอพักครั้งแรก
- ย้ายบ้านหรือย้ายคอนโด
- จัดห้องนอนหรือพื้นที่ทำงาน
- เตรียมของสำหรับเดินทาง
- เตรียมของสำหรับสัตว์เลี้ยง
- เริ่มต้นทำกิจกรรมหรือไลฟ์สไตล์ใหม่
- ค้นหาสินค้าภายใต้งบประมาณที่กำหนด

ระบบจะใช้ Template ค่อย ๆ ถามข้อมูลที่จำเป็น จากนั้นสรุปออกมาเป็นรายการสิ่งของ พร้อมแบ่งตามระดับความสำคัญ เช่น:

- จำเป็นต้องซื้อ
- ไว้ซื้อภายหลัง
- มีอยู่แล้ว
- ไม่จำเป็น
- หาซื้อใกล้บ้าน
- ต้องค้นหาข้อมูลเพิ่มเติม

ผู้ใช้สามารถดูสินค้าแนะนำ เพิ่มสินค้าไว้ในรายการ และค้นหาสินค้าเพิ่มเติมผ่านหน้าสนทนาได้

## 2. เป้าหมายของการออกแบบ

การออกแบบต้องช่วยให้ผู้ใช้รู้สึกว่า:

- เริ่มต้นได้ง่ายแม้ไม่มีความรู้เรื่องสินค้า
- ระบบกำลังช่วยคิดและจัดระเบียบข้อมูลให้
- ไม่จำเป็นต้องตัดสินใจทุกอย่างพร้อมกัน
- มองเห็นสิ่งที่จำเป็นก่อนสิ่งที่สำคัญน้อยกว่า
- เข้าใจเหตุผลของคำแนะนำ
- สามารถกลับมาแก้ไขหรือค้นหาเพิ่มได้ตลอด
- การเตรียมของเป็นเรื่องเบาและจัดการได้

เป้าหมายหลักคือ **ลดความสับสนและช่วยให้ผู้ใช้ตัดสินใจได้ง่ายขึ้น** ไม่ใช่แสดงสินค้าให้มากที่สุด

## 3. บุคลิกของแบรนด์

### 3.1 บุคลิกหลัก

- อบอุ่น
- เป็นมิตร
- ช่วยเหลือ
- น่าเชื่อถือ
- เรียบง่าย
- สดใส
- น่ารักเล็กน้อย
- พรีเมียมแบบนุ่มนวล
- เน้นการเลือกซื้อสินค้าอย่างมีเหตุผล

### 3.2 ความรู้สึกที่ต้องการสื่อ

ผลิตภัณฑ์ควรให้ความรู้สึกเหมือน:

- เพื่อนที่ช่วยเตรียมของให้ครบ
- ผู้ช่วยส่วนตัวด้านการเลือกสินค้า
- ระบบที่คอยแนะนำโดยไม่กดดัน
- จุดเริ่มต้นสำหรับคนที่ยังไม่รู้ว่าจะซื้ออะไร
- เครื่องมือที่ช่วยลดความยุ่งยากในการค้นหาสินค้า

### 3.3 สิ่งที่ไม่ควรเป็น

- Marketplace ที่มีข้อมูลแน่นเต็มหน้าจอ
- แอปที่เน้นโปรโมชั่นหรือเร่งให้ซื้อ
- ระบบที่ดูเป็นเทคนิคและซับซ้อน
- UI ที่ใช้สีจัดจ้านหลายสีพร้อมกัน
- แอปที่ดูเป็นเด็กหรือการ์ตูนมากเกินไป
- ระบบ Corporate ที่แข็งและห่างเหิน
- หน้าจอที่เต็มไปด้วย Card, Border และ Shadow

## 4. หลักการออกแบบ

### 4.1 เริ่มต้นง่าย

ทุกหน้าต้องทำให้ผู้ใช้เข้าใจได้ทันทีว่าต้องทำอะไรต่อ

- หนึ่งหน้าควรมีงานหลักเพียงหนึ่งอย่าง
- CTA หลักต้องเด่นและหาเจอง่าย
- ไม่แสดงตัวเลือกมากเกินไปพร้อมกัน
- ข้อมูลซับซ้อนควรถูกแบ่งเป็นขั้นตอน
- ใช้คำอธิบายสั้นและตรงประเด็น

### 4.2 ช่วยตัดสินใจ

ระบบต้องช่วยลดภาระในการคิดของผู้ใช้

- แบ่งระดับความจำเป็นอย่างชัดเจน
- อธิบายเหตุผลของคำแนะนำ
- สรุปข้อมูลให้อ่านง่าย
- แนะนำตัวเลือกที่แตกต่างกันอย่างมีเหตุผล
- ไม่แสดงสินค้าที่คล้ายกันมากเกินไป

### 4.3 เป็นมิตรและน่าเชื่อถือ

- ใช้สีอบอุ่นและรูปทรงมน
- ใช้มาสคอตในจังหวะที่เหมาะสม
- ข้อมูล ราคา และเหตุผลต้องอ่านง่าย
- หลีกเลี่ยงลูกเล่นที่รบกวนการใช้งาน
- ความน่ารักต้องไม่ลดความน่าเชื่อถือ

### 4.4 ลำดับข้อมูลต้องชัดเจน

ลำดับข้อมูลทั่วไป:

1. ชื่อหน้าหรือคำถามหลัก
2. คำอธิบายสั้น
3. ตัวเลือกหรือผลลัพธ์หลัก
4. ข้อมูลสนับสนุน
5. การกระทำรอง
6. CTA หลัก

### 4.5 ใช้ระบบเดิมก่อนสร้างใหม่

- ใช้ Component ที่มีอยู่ก่อนสร้าง Component ใหม่
- ใช้สีจาก Design Token เท่านั้น
- ใช้ Spacing และ Radius จากระบบ
- Component ประเภทเดียวกันต้องมีโครงสร้างเดียวกัน
- ห้ามสร้างรูปแบบพิเศษเฉพาะหน้าหากไม่มีเหตุผล

### 5.7 กฎการใช้สี

- ใช้ Primary เฉพาะ CTA หลัก สถานะ Selected และจุดเน้นสำคัญ
- หนึ่งพื้นที่ควรมี CTA หลักที่เด่นที่สุดเพียงหนึ่งจุด
- ไม่ใช้ Primary กับทุกปุ่มและทุก Icon
- ใช้ Background และ Surface เป็นสัดส่วนหลักของหน้าจอ
- สี Error ต้องแตกต่างจาก Primary อย่างชัดเจน
- ไม่ใช้สีแดงหรือสี Error กับการกระทำทั่วไป
- หลีกเลี่ยงพื้นหลังเข้มขนาดใหญ่
- ไม่เพิ่มสีใหม่โดยไม่บันทึกในเอกสารนี้
- ไม่ใช้ Gradient จนกว่าจะมีรูปแบบที่กำหนดอย่างเป็นทางการ
- ห้ามใช้สีเพียงอย่างเดียวเพื่อบอกสถานะ
- ตรวจสอบ Contrast ก่อนนำไปใช้จริงเสมอ

## 6. ระบบตัวอักษร

### 6.1 Font Family

```css
font-family: "LINE Seed Sans", "Sukhumvit Set", sans-serif;
```

| ฟอนต์ | บทบาท |
|---|---|
| `LINE Seed Sans` | ฟอนต์หลักสำหรับข้อความ UI ทั้งภาษาไทยและอังกฤษ |
| `Sukhumvit Set` | ฟอนต์สำรองสำหรับอุปกรณ์ Apple หรือกรณีที่ LINE Seed Sans ไม่พร้อมใช้งาน |
| `sans-serif` | System fallback |

กฎ:

- ใช้ LINE Seed Sans เป็นฟอนต์หลักทั้งระบบ
- ไม่ผสมฟอนต์ในหน้าเดียวกันเพื่อสร้างลำดับ
- ใช้ขนาด น้ำหนัก และสีเพื่อสร้าง Hierarchy
- Sukhumvit Set ใช้เป็น Fallback
- ห้ามเพิ่มฟอนต์ใหม่โดยไม่อัปเดตเอกสารนี้

### 6.2 ขนาดตัวอักษร

ขนาดต่ำสุดที่อนุญาตคือ **13px**

|---|---:|---:|---:|---|
| `display-large` | 40px | 52px | 700 | Hero ขนาดใหญ่ |
| `display` | 36px | 48px | 700 | Onboarding Headline |

| `heading-2` | 28px | 38px | 700 | หัวข้อสำคัญ |
| `heading-3` | 24px | 34px | 600 | หัวข้อ Section |
| `heading-4` | 20px | 30px | 600 | ชื่อ Card หรือสินค้า |
| `body-large` | 18px | 28px | 400 | คำอธิบายเด่น |
| `body` | 16px | 26px | 400 | เนื้อหาทั่วไป |
| `body-small` | 14px | 22px | 400 | ข้อมูลรอง |
| `label-large` | 16px | 24px | 500 | ปุ่มหลักและตัวเลือก |
| `label` | 14px | 20px | 500 | Chip, Tab และปุ่มขนาดเล็ก |
| `caption` | 13px | 18px | 400 | Metadata และคำอธิบายขนาดเล็ก |

### 6.3 Font Weight

| Token | Weight | การใช้งาน |
|---|---:|---|
| `regular` | 400 | เนื้อหาทั่วไป |
| `medium` | 500 | Label ปุ่ม และข้อมูลที่ต้องการเน้นเล็กน้อย |
| `semibold` | 600 | ชื่อ Card และหัวข้อ Section |
| `bold` | 700 | หัวข้อหลักและข้อความสำคัญ |

### 6.4 กฎ Typography

- ขนาดตัวอักษรต่ำสุดคือ 13px
- ข้อความหลักควรใช้ขนาดอย่างน้อย 16px
- ปุ่มหลักควรใช้ขนาดอย่างน้อย 16px
- หัวข้อหนึ่งหน้าควรมี Heading 1 เพียงหนึ่งจุด
- หลีกเลี่ยงการใช้ Bold กับย่อหน้ายาว
- ภาษาไทยต้องมี Line-height ประมาณ 1.45–1.65 เท่าของขนาดตัวอักษร
- ข้อความหลายบรรทัดไม่ควรจัดกึ่งกลาง ยกเว้น Onboarding และ Empty state
- ข้อมูลสำคัญไม่ควรถูกตัดโดยไม่มีวิธีดูฉบับเต็ม
- ใช้ Ellipsis เฉพาะพื้นที่จำกัดจริง
- ห้ามใช้สีอ่อนจนข้อความอ่านยาก

## 8. Layout สำหรับ Mobile

### 8.1 ขอบเขตการออกแบบ

- ล็อกการออกแบบเป็น Mobile Web App เท่านั้นในระยะนี้
- ใช้โครงสร้าง Single-column เป็นหลัก
- ออกแบบสำหรับการใช้งานด้วยนิ้ว
- ไม่ต้องออกแบบ Tablet หรือ Desktop จนกว่าจะมีการยืนยันเพิ่มเติม
- ทุกหน้าต้องรองรับความกว้าง Mobile ที่แตกต่างกันโดยไม่เกิด Horizontal scroll
- เนื้อหาสำคัญต้องไม่ชิดขอบหน้าจอหรือถูกบังด้วย Browser UI

### 8.2 ขนาดหน้าจออ้างอิง

| Token | ความกว้าง |
|---|---:|
| `mobile-small` | 320–374px |
| `mobile-default` | 375–429px |
| `mobile-large` | 430–767px |

ให้ใช้ความกว้างประมาณ 390px เป็นหน้าจอหลักสำหรับออกแบบ และตรวจสอบซ้ำอย่างน้อยที่ 320px และ 430px

### 8.3 Page Padding

| ขนาดหน้าจอ | Padding ด้านข้าง |
|---|---:|
| 320–374px | 16px |
| 375–429px | 20px |
| 430px ขึ้นไป | 24px |

### 8.4 Content Width

- เนื้อหาหลักใช้ความกว้างเต็มพื้นที่ภายใน Page padding
- Form, Question flow, Chat และ Result ใช้ 1 Column
- ไม่กำหนดความกว้างแบบ Desktop
- Card และปุ่มหลักสามารถกว้างเต็ม Container
- ข้อความยาวต้องตัดบรรทัดได้โดยไม่ทำให้ Layout แตก

### 8.5 Vertical Layout

โครงสร้างหน้าทั่วไป:

```text
Safe area ด้านบน
Top area / Header
Page title หรือ Question
Supporting content
Main content
พื้นที่เผื่อ Sticky action
Sticky bottom action
Safe area ด้านล่าง
```

### 8.6 Sticky Bottom Action

- ใช้กับ Flow ที่มี CTA หลัก เช่น “ถัดไป” หรือ “ดูรายการ”
- ต้องมีพื้นหลังแยกจาก Content
- ต้องเผื่อพื้นที่ด้านล่างของ Content เพื่อไม่ให้รายการสุดท้ายถูกบัง
- รองรับ Home indicator และ Browser toolbar
- เมื่อ Keyboard เปิด ต้องไม่บัง Input หรือปุ่มที่จำเป็น

### 8.7 Safe Area

```css
padding-top: max(16px, env(safe-area-inset-top));
padding-bottom: max(16px, env(safe-area-inset-bottom));
```

### 8.8 กฎ Mobile Layout

- Touch target ขั้นต่ำ 44×44px
- ไม่วางปุ่มสำคัญชิดขอบหน้าจอ
- ไม่ใช้ Hover เป็นวิธีหลักในการสื่อสถานะ
- ไม่ใช้ Layout หลายคอลัมน์สำหรับเนื้อหาหลัก
- ตารางต้องแปลงเป็น List หรือ Card เมื่อแสดงบน Mobile
- Tab หรือกลุ่มตัวเลือกที่กว้างเกินพื้นที่ต้องเลื่อนได้ หรือเปลี่ยนรูปแบบให้เหมาะสม
- ต้องตรวจสอบการแสดงผลเมื่อข้อความภาษาไทยยาวขึ้น
- ต้องรองรับ Browser zoom โดย Layout ไม่แตก
- ไม่ออกแบบ Tablet และ Desktop จนกว่าจะมีการปลดล็อกขอบเขต

## 12. Loading, Empty, Error และ Success

### Loading

- ใช้ Skeleton สำหรับ Card และ List
- ใช้ Spinner สำหรับงานสั้น
- ไม่ปล่อยหน้าว่าง
- ไม่เปลี่ยน Layout เมื่อข้อมูลโหลดเสร็จ

### Empty State

- Illustration หรือ Icon
- หัวข้อ
- คำอธิบาย
- CTA ที่ชัดเจน

### Error State

- อธิบายปัญหาแบบเข้าใจง่าย

- ไม่แสดงรหัสเทคนิค

### Success State

- ยืนยันสิ่งที่เกิดขึ้น
- แนะนำขั้นตอนต่อไป
- ใช้ Toast สำหรับการสำเร็จขนาดเล็ก
- ใช้หน้าสำเร็จสำหรับจุดสำคัญ

## 14. Motion

Motion ของระบบเน้นการเคลื่อนไหวจาก Illustration และมาสคอต เพื่อช่วยอธิบายสถานะของระบบ มากกว่าการใช้ Transition ซับซ้อนหรือ Animation ตกแต่งหลายจุด

### รูปแบบ Motion หลัก

รูปแบบที่ใช้บ่อยที่สุดคือ:

- Illustration หรือมาสคอตอยู่กึ่งกลางหน้าจอ
- ภาพค่อย ๆ ขยายและย่ออย่างนุ่มนวล
- มีข้อความอธิบายสถานะอยู่ด้านล่าง
- อาจมีข้อความรองเพื่อบอกว่าระบบกำลังทำอะไร
- ใช้ในสถานะที่ผู้ใช้ต้องรอ เช่น Loading, Processing, Searching และ Generating result

ตัวอย่างข้อความ:

- “กำลังค้นหาสินค้าที่เหมาะกับคุณ”
- “กำลังจัดรายการของที่จำเป็น”
- “ขอเวลาสักครู่ เรากำลังเปรียบเทียบตัวเลือกให้”
- “กำลังสรุปผลลัพธ์จากคำตอบของคุณ”
- “กำลังค้นหาตัวเลือกเพิ่มเติม”

### Illustration Loading

องค์ประกอบหลัก:

1. Illustration หรือมาสคอต
2. ข้อความสถานะหลัก
3. ข้อความอธิบายเพิ่มเติม เมื่อจำเป็น
4. Progress indicator เฉพาะกรณีที่สามารถบอกความคืบหน้าได้จริง

แนวทางการเคลื่อนไหว:

- ใช้การขยายและย่อแบบเบา ๆ
- Scale แนะนำประมาณ `1` ถึง `1.06`
- ไม่ควรขยายจนภาพดูเด้งหรือรบกวนสายตา
- ใช้การเคลื่อนไหวต่อเนื่องและนุ่ม
- สามารถเพิ่มการลอยขึ้นลงเล็กน้อยได้ หากไม่ทำให้ภาพดูวุ่นวาย
- ไม่ควรหมุนภาพทั้งชิ้น
- ไม่ควรใช้ Bounce แรง
- ไม่ควรใช้หลาย Motion พร้อมกัน

ตัวอย่าง:

```css
@keyframes illustration-breathe {
  0%,
  100% {
    transform: scale(1);
  }

  50% {
    transform: scale(1.06);
  }
}

.loading-illustration {
  animation: illustration-breathe 1.8s ease-in-out infinite;
  transform-origin: center;
}
```

### จังหวะและระยะเวลา

| Motion | ระยะเวลาแนะนำ |
|---|---:|
| Illustration ขยาย–ย่อ | 1.6–2.2 วินาทีต่อรอบ |
| Fade in ข้อความ | 200–300ms |
| เปลี่ยนข้อความสถานะ | 250–350ms |
| แสดงผลลัพธ์หลังโหลดเสร็จ | 300–450ms |
| Feedback ของปุ่ม | 100–150ms |

### การจัดวาง Loading State

- Illustration อยู่เหนือข้อความ
- เว้นระยะระหว่างภาพกับข้อความประมาณ 24–32px
- ข้อความหลักใช้ `heading-4` หรือ `body-large`
- ข้อความรองใช้ `body` หรือ `body-small`
- ข้อความควรจัดกึ่งกลาง
- จำกัดความกว้างข้อความเพื่อไม่ให้ยาวเกินไป
- ไม่แสดงข้อความเกิน 2–3 บรรทัด
- หากเป็น Full-screen loading ให้จัดกลุ่มทั้งหมดใกล้กึ่งกลางแนวตั้ง
- หากเป็น Inline loading ให้ลดขนาด Illustration และข้อความตามพื้นที่

### ประเภทการใช้งาน

#### Full-screen Loading

ใช้เมื่อ:

- กำลังประมวลผลคำตอบทั้งหมด
- กำลังสร้างผลลัพธ์จาก Template
- กำลังค้นหาสินค้าจำนวนมาก
- กำลังเตรียมรายการแนะนำครั้งแรก

ลักษณะ:

- ใช้ Illustration ขนาดใหญ่
- มีข้อความหลักและข้อความรอง
- ไม่ควรมีปุ่มอื่นแย่งความสนใจ
- สามารถมีปุ่ม “ยกเลิก” ได้ หากกระบวนการใช้เวลานานและยกเลิกได้จริง

#### Section Loading

ใช้เมื่อ:

- โหลดข้อมูลเพียงบางส่วน
- โหลดรายการสินค้า
- โหลดข้อความตอบกลับใน Chat

ลักษณะ:

- Illustration ขนาดเล็กลง
- ใช้ข้อความสั้น
- ไม่บังข้อมูลส่วนอื่นของหน้า
- หากโครงสร้างข้อมูลชัดเจน สามารถใช้ Skeleton ร่วมได้

#### Chat Thinking State

ใช้เมื่อระบบกำลังคิดหรือค้นหาในหน้า Chat

ลักษณะ:

- ใช้มาสคอตหรือ Illustration ขนาดเล็ก
- มีข้อความ เช่น “กำลังช่วยค้นหาให้”
- อาจใช้การขยาย–ย่อหรือจุดเคลื่อนไหวแบบเบา
- ไม่ควรใช้ Spinner อย่างเดียว หากสามารถสื่อสารด้วยภาพและข้อความได้

### Progress Indicator

- ใช้ Progress bar หรือเปอร์เซ็นต์เฉพาะเมื่อระบบทราบความคืบหน้าจริง
- ห้ามแสดงเปอร์เซ็นต์จำลอง
- หากไม่ทราบระยะเวลา ให้ใช้ Illustration Motion และข้อความสถานะแทน
- สามารถเปลี่ยนข้อความตามขั้นตอนจริงได้ เช่น “กำลังวิเคราะห์” → “กำลังเปรียบเทียบ” → “กำลังสรุปผล”

### Motion รอง

Motion อื่นยังสามารถใช้ได้ แต่ต้องเป็นองค์ประกอบสนับสนุน:

- Fade in / Fade out
- Slide เล็กน้อยเมื่อเปลี่ยนขั้นตอน
- Feedback เมื่อกดปุ่ม
- การเพิ่มสินค้าเข้ารายการ
- การเปิดหรือปิดรายละเอียด
- Success feedback แบบสั้น

Motion รองต้องไม่เด่นกว่าการเคลื่อนไหวของ Illustration และต้องไม่เกิดหลายจุดพร้อมกัน

### กฎ Motion

- ใช้ Illustration Motion เป็นรูปแบบหลักของ Loading
- ทุก Loading ที่ใช้เวลามากกว่าเล็กน้อยควรมีข้อความอธิบาย
- ข้อความต้องบอกว่าระบบกำลังทำอะไร ไม่ใช้เพียงคำว่า “กำลังโหลด”
- Motion ต้องนุ่ม สงบ และเข้ากับบุคลิก Warm, Friendly และ Soft Premium
- ไม่ใช้ Animation เพื่อความสวยงามอย่างเดียว
- ไม่ใช้ Motion ที่ทำให้ผู้ใช้รู้สึกว่ารอนานขึ้น
- ไม่ใช้ Bounce, Shake หรือ Spin ที่แรง
- ไม่ใช้ Animation หลายจุดพร้อมกัน
- ไม่เปลี่ยนข้อความเร็วเกินจนอ่านไม่ทัน
- เมื่อโหลดเสร็จ ให้ Transition ไปยังผลลัพธ์อย่างนุ่มนวล
- รองรับ `prefers-reduced-motion`

### Reduced Motion

เมื่อผู้ใช้เปิด `prefers-reduced-motion`:

- ปิด Animation แบบขยาย–ย่อต่อเนื่อง
- แสดง Illustration แบบนิ่ง
- ใช้ Fade สั้น ๆ หรือเปลี่ยนสถานะแบบทันที
- คงข้อความอธิบายสถานะไว้
- ห้ามซ่อนข้อมูลสำคัญเพราะปิด Motion

```css
@media (prefers-reduced-motion: reduce) {
  .loading-illustration {
    animation: none;
  }
}
```

## 15. Accessibility

- ขนาดตัวอักษรต่ำสุด 13px
- Body หลักอย่างน้อย 16px
- Button หลักอย่างน้อย 16px
- รองรับ Browser zoom อย่างน้อย 200%
- ข้อความทั่วไปต้องผ่าน WCAG AA
- ไม่ใช้สีเพียงอย่างเดียวเพื่อบอกสถานะ
- ทุก Interactive element ใช้ Keyboard ได้
- Focus state ต้องมองเห็นชัด
- รูปภาพสำคัญมี Alt text
- Icon button มี Accessible label
- พื้นที่กดขั้นต่ำ 44×44px

- ไม่ใช้ศัพท์เทคนิคโดยไม่จำเป็น

ควรใช้:

- “เริ่มต้นค้นหาของที่คุณต้องการ”
- “เราช่วยจัดรายการให้คุณได้”
- “คุณสามารถกลับมาแก้ไขภายหลังได้”
- “สินค้านี้เหมาะกับเงื่อนไขที่คุณเลือก”
- “ลองบอกงบประมาณที่คุณสะดวก”
- “ยังไม่แน่ใจใช่ไหม เราช่วยค้นหาเพิ่มได้”

หลีกเลี่ยง:

- “คุณต้องซื้อสินค้านี้”
- “ดีที่สุดสำหรับทุกคน”
- “ซื้อเลยก่อนหมด”
- “ห้ามพลาด”
- ข้อความสร้างแรงกดดันโดยไม่มีเหตุผล

---

## 17. ราคาและข้อมูลสินค้า

- ใช้รูปแบบราคาเดียวกันทั้งระบบ เช่น `1,290 บาท`
- ช่วงราคาใช้รูปแบบ `240–500 บาท`
- ถ้าไม่ใช่ราคาปัจจุบัน ให้ระบุว่า “ราคาประมาณ”
- แยกข้อมูลจากร้านค้ากับคำแนะนำของระบบ
- สินค้า Affiliate หรือ Sponsored ต้องมี Label ชัดเจน
- ไม่ใช้คะแนนหรือรีวิวปลอมใน Production
- ระบุวันที่อัปเดตราคาเมื่อข้อมูลอาจเปลี่ยนแปลง

---

## 18. ความโปร่งใสของคำแนะนำ

สินค้าแนะนำควรมีเหตุผล เช่น:

- เหมาะกับงบประมาณ
- เหมาะกับพื้นที่ขนาดเล็ก
- เหมาะกับผู้เริ่มอยู่หอ
- สามารถซื้อภายหลังได้
- ใช้งานได้หลายรูปแบบ
- ประหยัดพื้นที่
- ดูแลรักษาง่าย
- หาซื้อหรือเปลี่ยนอะไหล่ง่าย

---

## 19. สิ่งที่ควรทำ

- ใช้พื้นที่ว่างอย่างเพียงพอ
- แสดงหนึ่งงานหลักต่อหน้า
- ใช้ Primary เฉพาะจุดสำคัญ
- ใช้ Component เดิมก่อนสร้างใหม่
- อธิบายเหตุผลของคำแนะนำ
- ให้ผู้ใช้ย้อนกลับและแก้ไขได้
- ใช้ข้อความสั้นและตรงประเด็น
- ออกแบบ Loading, Empty, Error และ Success
- รักษา Radius, Border และ Spacing ให้สม่ำเสมอ
- ออกแบบและตรวจสอบเฉพาะ Mobile ในระยะนี้

---

## 20. สิ่งที่ไม่ควรทำ

- ไม่ใส่ทุก Section ไว้ในการ์ด
- ไม่ใช้ Primary เต็มหน้าจอ
- ไม่ใช้เงาหนัก
- ไม่ใช้ Gradient โดยไม่มีระบบ
- ไม่ใช้ Icon หลายสไตล์
- ไม่ใช้ข้อความขายของมากเกินไป
- ไม่แสดงสินค้ามากจนเลือกไม่ถูก
- ไม่สร้าง Component เฉพาะหน้าโดยไม่จำเป็น
- ไม่ใช้ Modal สำหรับทุก Feedback
- ไม่ทำ UI ให้เหมือน Marketplace ทั่วไป
- ไม่ให้มาสคอตแย่งความสนใจจากงานหลัก
- ไม่ใช้ตัวอักษรต่ำกว่า 13px

---

## 21. แนวทางสำหรับ AI, Designer และ Developer

ก่อนสร้างหรือแก้ไขหน้าจอ ต้อง:

1. อ่านเอกสารนี้
2. ตรวจสอบ Component ที่มีอยู่
3. ใช้ Design Token ที่กำหนด
4. รักษาทิศทาง Warm, Friendly, Helpful และ Soft Premium
5. ระบุงานหลักของหน้าให้ชัด
6. ออกแบบทุก State ที่เกี่ยวข้อง
7. ตรวจสอบการแสดงผลอย่างน้อยที่ความกว้าง 320px, 390px และ 430px
8. ตรวจสอบ Keyboard และ Screen reader
9. ใช้ภาษาไทยที่อ่านง่าย
10. ไม่เพิ่มสี ฟอนต์ Radius หรือ Shadow ใหม่เอง

เมื่อสร้าง Component ใหม่ ต้องระบุ:

- จุดประสงค์
- สถานการณ์ที่ใช้
- โครงสร้างข้อมูล
- ขนาด
- Padding และ Gap
- สี
- Typography
- State
- Responsive behavior
- Accessibility behavior

หากข้อมูลไม่เพียงพอ:

- ใช้ Component ที่ใกล้เคียงที่สุด
- ไม่สร้างทิศทางภาพใหม่เอง
- ระบุข้อมูลนั้นเป็น `[รอยืนยัน]`
- ไม่ถือว่าข้อมูลที่เดาเป็นข้อสรุปจริง
